## Root cause (verified, and it's not what the attempted fix targeted)

The worklog already contains the key data. Pair 415's **gap never moved**. What changed was which *bucket* it was counted in:

- Before K5: `min hFel = 8.47 km` → `COL.isClosingCC` true → the pair is measured against the **crush floor** (0.05 w0), so it is invisible to the ordinary-floor check. The post-finalFloor ordinary minimum is a *different* pair at `0.1200 w0`.

- K5 runs `collapse` → `belt` → `beltLocal` → arc → lip → `delaminate`. The local-gradient term strips felsic: `8.47 → 8.04 → 6.41 km`.

- After K5: `hFel = 6.41 km < P.hOceanic (8 km)` → `isClosingCC` flips false → pair 415 is ejected from the crush bucket into the **ordinary bucket**, where its unchanged `0.0678 w0` gap (~5.3 km) now fails the 9.38 km ordinary floor.

Two facts make this an artifact rather than a geometry failure:

1. **K5 does not touch `colX`.** Collapse, belt, beltLocal, zDyn, arc, lip and delaminate all mutate stack thicknesses and elevations — none moves a column horizontally. So the gap at finalFloor and at K5 is *the same number*. The `0.1200 → 0.0678` shift in the reported minimum is purely a reclassification.

2. **The pair is physically fine.** A 5.3 km gap between two continental columns carrying 6.4 km of felsic each sits comfortably above the 3.91 km crush floor. It only fails because it got reclassified into a stricter bucket.

The deeper fragility: `isClosingCC` uses `hFel >= hOceanic` as the continent test, and `hFel` is a *cache of the stack* that K5's redistribution actively depletes. So the floor solve runs once (at K4/finalFloor), grants the crush exemption, and then a later K5 stage silently revokes it by draining the very quantity the exemption was keyed on. The classification is recomputed downstream of the step that depletes it.

## Why the attempted fix was the wrong lever

Gating `beltLocal` on continental classification attacks the *operator that causes the depletion*. It leaves the *predicate that reclassifies the pair* untouched — and it changes belt behavior planet-wide, which is exactly the broad regression the agent saw. The defect is in the classification/floor coupling, not in the transport operator.

## Recommended next step

Target the coupling, not the operator. The cleanest, smallest change: **make the closing-C–C classification a settled per-frame fact rather than a per-stage measurement.** Compute it once where the topology is already settled (at K4 / `finalFloor`, before K5), store it, and have `COL.floor` read the stored classification. Then K5's crustal redistribution cannot revoke a floor already granted — because the floor solve legitimately runs before K5 and the gap is provably unchanged through K5.

This is different from what the worklog says was already tried and rejected ("a post-K5 floor call worsened minima and caused an R3 failure") — that adds a *second* floor solve after K5; this instead *freezes the classification* that the existing single solve uses. Worth distinguishing clearly.

Before coding it, convert the inference into a measurement with a cheap targeted probe: capture `colX`, `colU`, `hFel` and `isClosingCC` for pair 415 at the finalFloor hook and again inside the K5 wrapper on the failing frame, and confirm the gap is byte-identical while the classification flips. That's the "measured, not fitted" foundation this tree requires, and it pins down exactly which pairs change bucket so the fix can be verified against all four strict legs rather than guessed.

Then: implement the frozen classification, rerun `m2-check.js`, the four strict `contact-audit` legs, the R4 matrix, and the mass/replay/default-planet suite. Keep `kBeltGradient = 8`, `gFloor`, `crushGap`, `hOceanic` and all belt thresholds unchanged.
