# 0.3.0-P3.0 worklog — the pool, the phases, and what they cost

Plan of record: `0.3.0-p3-plan.md` §4 P3.0 (gate: no allocation in frame kernels, no dropped
material at capacity, P2 regression green), with §1 contracts, §2 phase table, §5 budget and §6
interfaces. The request, verbatim: "0.3.0‑P3 (conserved melt / eruption pool‑ledger for the
particle engine) — the pile rule it was waiting on is now in place." The prerequisite is
0.2.5's pile-before-death write-back (`archive/0.2.5-pile-before-death-worklog.md`), which has
landed (`ERUPT.writeBack` at vent death only, acceptance 49/49). P3 does not touch the column
engine (`js/*.js`, `columns.html`).

This is P3.0 only. No melt, no eruption, no flight, no landing yet: the pool exists, the
phases exist, and every kernel routes by phase. Each later milestone adds behaviour to a
routing that is already measured.

### 1.1 The phase routing, as measured

`experiments/pt-p3-routing.js` probes each phase through each pass with a loud sentinel (a
clast with mass, strength, damage and a fake cluster id) and reports what changed. The table
is what the code does, not what the plan says:

```
  phase             deposit  conduct  flow map  advect  repair  crust  surface
  mantle            yes      yes      yes       yes     yes     yes    yes
  melt              yes      yes      no        no      yes     no     no
  airborne          no       no       no        no      no      no     no
  deposit above     yes      yes      yes       yes     no      yes    yes
  deposit inside    yes      yes      yes       yes     yes     yes    yes
```

Airborne parcels are in no pass: they are wall-time only, and are excluded from repair,
conduction, clusters and the crust diagnostics. Mobile melt is grid-coupled and nothing
else. A landed deposit is coupled, rides the flow map and welds. An above-surface deposit is
not repair material (`e < 0` is not a donor).

### 1.2 Enthalpy neutrality at P3.0

At P3.0 `gatherDT` writes the same `d` to `T` and to `H`, and the same `tot` to `ledger` and
`hLedger`. So `H ≡ T` and `hLedger ≡ ledger` **bitwise** (−6770.000605897095 both after 20
frames). This is deliberate: P3.1 breaks the identity with the enthalpy/partial-melt
equilibrium, and the fixture's bitwise assertion is what will show the break. The adjoint
identity survives because `scatterT` and `gatherDT` gate on the same coupled set.

## 2. The pool's transactions (`pt-p3-pool.js`)

- `admit(S, ph)` zeroes every field, sets `id = nextId++`, and at capacity returns −1 and
  counts `tx.refuse`. Nothing is dropped silently.
- `split(S, p, frac, ph)` takes a **proper** fraction only (`0 < frac < 1`). A whole parcel is
  a phase change (P3.1), so `frac = 1` is refused. The child copies the intensive state;
  `age/dmg/mu` reset; the host keeps its id. At capacity the split is deferred and counted,
  and the mass stays in the host.
- `merge(M, S, a, b)` is same-phase only; it sums mass, momentum and enthalpy, mass-weights
  `H, T, cF, cW, melt, age, y, e`, folds `dx` into `[−wrap/2, wrap/2)`, keeps the smaller
  id, and removes `b`. `y` and `e` are mass-weighted independently (not recomputed from each
  other).
- `remove(S, p)` compacts the last active slot over `p` across every `FIELDS` array and
  counts `tx.move`.

Measured: 256 splits close mass to |d| 2.98e-8 on 4.17e7 (≈7e-16 relative), enthalpy to
7.45e-9, momentum to ≤2.7e-9 on 3.4e7. Merge formulas are exact (relative 0);
`merge(a,b) ≡ merge(b,a)`; split→merge round trip ≤3e-16. 4711 splits fill the reserve
exactly to 28263 with mass drift 5.22e-6 (1.25e-13 relative) and no duplicate ids. A refused
split+admit changes only `tx.refuse`. The fingerprint is sensitive to `id/ph/H/cF/cW/melt/m/T`
and to `nextId` and `tx`. The same seed and the same transaction script replay bitwise. A
fresh planet's stock equals the mesh's interior node measure (|d| 3e-6 on 4.2e7 before the
accumulator fix in §4.2; exact after).

## 4. Review: defects found and fixed

### 4.1 Found while building the fixtures

1. `split` guard. First written as `!(frac >= 1)`, which accepts `frac = 1` as a split. Now
   `!(frac > 0) || !(frac < 1)`, so a whole-parcel "split" is refused.
2. `state.reset` tail clears ran after the placement loop, so `fill(0)` wiped the seeded
   values. All new material arrays use `fill(v, p)` from the prefix end.
3. `S.tx` must exist at module load: `hash()` dereferences it and fixtures call it before
   `init()`. It is an object literal in `PTS`.
4. Reseed on `PH_GRID` alone was not enough: an above-surface deposit (`e < 0`) clamps to
   row 1 in `nodeOf` and would be borrowed as a donor. The donor test also requires
   `S.e[p] >= 0`.
5. A refused transaction changes `hash()`, because `tx.refuse` is in it. The "refusal changed
   nothing" check now saves and restores `tx.refuse` around the comparison, so it proves that
   only the counter differs.
6. `SIM.init()` rebuilds the mesh object; fixtures must take `M` from `configure()` after it,
   never an older one.

### 4.2 Found by the budget harness: the compensated sum was not compensating

`pool.js` `cadd` had its two Fast2Sum branches swapped. When the running sum was the larger
term it used `a − (s − b)`, and when `v` was larger it used `b − (s − a)`; each is valid only
for the other order. The result was that `inventoryComp` returned exactly the naive sum
(`41688446.70242976`) while a direct Neumaier sum gave `41688446.7024328`: a 3e-6 km² error,
7e-14 relative.

The pool fixture passed with the bug, because it compared the compensated pass with the naive
one, and the two agreed by construction. Fixed the branch order. Then:

- the pool fixture gained a direct Neumaier cross-check over the same parcels, gated at
  1e-14 relative. **Mutation test:** with the swapped branches reinserted, the fixture fails
  (absolute 3.04e-6 km², 7e-14 relative; 1 of 70); with the fix, all 70 pass. An earlier 1e-13 gate let the mutant
  through, because the error is 7e-14; the gate was tightened for that reason.
- the budget harness cross-checks the compensated mass and enthalpy against its own Neumaier
  sum at 1e-14 (rel 0).

Effect on other numbers: the routing and budget tallies shift by ~1e-6 absolute, because they
use the pool's totals. The physics is unchanged. The routing enthalpy closure is now 2.1e-8
absolute on 1.06e5 km²·H (2e-13 relative); it was 6.3e-7 absolute with the broken sum. Both are
inside the P1 tolerance. (`check.near` prints the absolute difference under its `rel` label:
read those numbers as absolute.)

### 4.3 Found in the probes and harnesses (harness defects, not engine defects)

7. The first routing table read `crust no` for mantle and `repair yes` for above-surface
   deposits, which were not the plan's expectations. Two probe-setup errors, not engine
   errors:
   - the crust column ran on a loud parcel at 5 K (hot: nothing welds at that temperature)
     and with age 0, so it measured "unwelded". The probe now sets the thermal state the
     crust pass needs (0.05 K, aged past the weld time) before `SC.crust`;
   - the repair column ran after advection, and advection had already reflected the deposit
     back inside the mesh, so the repair saw an interior parcel. The repair now runs before
     advection, because the question is where the parcel stands when the repair is decided.
   Both changes alter the probe, not the engine. The final table is the one the code gives,
   and it matches the expectation written in the fixture before the first run.
8. The budget harness's first run failed "the mass it gained" by 2.4e-6 km². The harness had
   summed the injected mass naively, against a compensated gain. It now uses its own Neumaier
   sum. The gain then closes to 1.6e-9 km² absolute on 6.2e5 (2.6e-15 relative). The
   residual is not attributed; it is far inside every gate here.
9. The budget harness's first inventory gate compared a total over 1000 calls (ms) with a
   per-call threshold. Rewritten as a per-call time against the frame budget.
10. The first draft of the reserve-price check invented pass thresholds (1.5× and 1.15×). Removed:
    the price is information, and the only gates are the plan's (the shipped rung fills the
    reserve exactly, and the shipped rung stays inside the §7 frame budget).
11. `pt-ui.js` first version expected `TS.n === partCap − 256`, which is the pre-P3.0 marker
    count. The reserve starts empty, so the check now expects `partBase`. The phase-line
    regex first failed on the separator (the HUD joins phases with two spaces, not one); a
    debug dump of the HUD text found it, and the dump was removed.

## 5. The reserve: measured, not frozen

The plan says the reserve is set by the benchmark. `pt-p3-budget.js` filled the reserve with
the phase mix the reserve names (melt : air : deposit in the reserves' own proportions) and
timed the full frame, at four reserve sizes and three rungs. Two runs, the same harness:

Ratio to the empty pool at the same rung, per run (run 1 and run 2 were the harness before the
window-spread column and the Neumaier fix; the final run is the kept log
`experiments/logs/0.3.0-p3.0-pt-p3-budget.txt`):

| rung | empty pool (run 1 / 2 / final) | reserve 0.10 | reserve 0.20 (shipped) | reserve 0.40 |
| --- | --- | --- | --- | --- |
| 256×24, mpc 4 | 11.7 / 12.8 / 9.9 ms | 0.94 / 0.92 / 1.08 | 1.17 / 1.02 / 1.19 | 1.12 / 1.06 / 1.20 |
| 512×48, mpc 2 | 24.6 / 20.7 / 19.7 ms | 1.08 / 1.06 / 1.20 | 0.94 / 1.26 / 1.22 | 1.05 / 1.50 / 1.37 |
| 1024×96, mpc 2 | 84.6 / 88.8 / 86.0 ms | 1.08 / 0.97 / 1.01 | 1.18 / 1.01 / 0.99 | 1.37 / 1.15 / 1.22 |

Final-run window spread (the widest of four windows against the best, per point): 256×24
14–36%, 512×48 6–37%, 1024×96 2–23%.

The shipped rung's frame with the reserve filled: 13.68 ms (run 1), 12.97 ms (run 2), 11.76 ms
(final).

What this says:

- The shipped rung at 256×24, with the reserve filled, measured 13.68, 12.97 and 11.76 ms
  across the three runs. Each is inside the 14 ms §7 budget, but the margin is 0.3 to 2.3 ms,
  and the first run was within 0.4 ms of the line. A frame at capacity with the pressure still
  on measured 13.27 ms in run 2.
- The reserve's price at 256×24 (0.40 against empty) reads +12%, +6% and +20% across the
  three runs. Every price sits inside the window spread of its own rung, and the runs disagree
  on the sign of the 0.10 price at 256×24. **The benchmark does not resolve the reserve's cost
  on this machine.**
- The 512×48 and 1024×96 rungs are over budget with or without a reserve (24 ms and ~86–105 ms
  filled). The plan promises no budget at those rungs (`0.3.0-p3-plan.md` §5; the
  `pt-check` gate is 256×24 only), so this is recorded, not acted on.

Decision recorded here: the candidate values `resMelt .05 / resAir .03 / resDep .12` stay in
`params.js`. The benchmark does not reject them, and it does not measure a better value. They
are **not frozen**: `partCap` is 28263 and a save would record it (plan §6), so freezing is a
decision for a quiet machine. Re-run `node experiments/pt-p3-budget.js` on an idle host
before freezing, and take the reserve from its shipped-rung row.

## 6. What the checks do not prove

- **Allocation.** Section C counts *typed-array* construction (a Proxy over the global
  constructors) and `ArrayBuffer` growth over 400 frames at capacity: zero. It does not count
  object or array literals, or closures, in the frame loop. Those are policed by reading and
  by AGENTS.md, not by a gate. The P3.0 gate names "no allocation in frame kernels"; the
  measured part is the typed-array part.
- **Closure.** Mass: 4711 splits drift 5.2e-6 km² on 4.2e7 (1.3e-13 relative); the live run's
  mass is unchanged to rounding. Enthalpy against the wall book: intake/wall 1.0000, and an
  absolute 2e-8 to 6e-7 km²·H on 1.06e5 (2e-13 to 6e-12 relative), depending on the tally. The
  plan's 1e-9 gate over the whole run, with compensated summation, is P3.5's
  (`pt-p3-check.js`); P3.0 does not claim it.
- **Enthalpy.** `H ≡ T` at P3.0 by construction (§1.2). A test that only passes because the two
  arrays are identical proves the routing and the bookkeeping, not the thermodynamics. P3.1
  is where that changes.
- **Airborne parcels.** They are in no pass, and their positions are bitwise unchanged over
  400 frames. Their flight is P3.4's. Their wall-time kernel does not exist yet.
- **The above-surface deposit.** An above-surface deposit that rides the flow map is
  reflected at the top wall by `keepInside`, which sends it back inside the mesh (the routing
  INFO line). Whether an edifice stands inside the fluid domain's top wall or above it is a
  P3.4 landing decision. P3.0 does not decide it.
- **Capacity.** Pressure is applied by explicit admissions and splits to the top, not by a
  natural eruption. Refusals are counted and nothing is lost, but the rate of refusals under
  real eruptive load is not measured (P3.3).
- **Timing.** The sandbox's frame times vary by 15–35% between windows (table in §5). Every
  timing claim in this worklog is a range over runs, not a point.
- **Save format.** None exists yet. `partCap` is what a future save will record.
