This repository already knew it — Phase A recorded *"the plan's `ee43f647…` resolves to no
commit there"* (`archive/0.4.2-phase-b-report.md` §1, B0), which is exactly why our manifest
pins `61f77aa`, the revision actually fetched, and why `0.4.2-plan.md` D1 resolves the
handoff **by hash, not by branch**. Their §1.1 restates the pin without that caveat.

The conclusion is unaffected and the caveat is not pedantry, for one concrete reason: **a
drift gate that reads its own manifest cannot run against a dangling SHA.** Ours runs and is
green (§1.2). The same check on their side — `git show ee43f647:port/slice-format.js` —
fails at the first command, so their manifest cannot self-verify the way ours can, and any
future session that tries will read a git error as drift.

Their §5 already recommends one coordinated manifest touch when something is scheduled. That
touch should fix **both** defects in the one change, since it is already open:
`section-reader` → the revision that landed the cutover *and* the restore (their note is
stale, as they say), and `globe-writer` → a revision that exists and carries the hashed
bytes. **Not before.** This side mirrors their hold (§4): a manifest touch with no artifact
behind it is churn, and a pin fix is not an artifact. Until then the operative authority on
both sides is the `files[]` sha256s, which is what D1 says anyway.

Mechanism, so this is not read as a test gap on their side: their `tests/port.js` is offline
by design and asserts the manifest's *shape* and each file's *bytes*; it never resolves a
commit, so a dangling pin cannot fail it. This repository's `experiments/upstream-drift.js`
does resolve the pin — that is its whole job — and it is green because our manifest pins
`61f77aa`, which exists. Neither suite reads the other side's manifest, so the dangling pin
is invisible to both and visible to a one-line `git cat-file -e`. That is the argument for
fixing it in the coordinated touch rather than legislating a new gate: a manifest pin is a
claim about a repository, and only that repository's own history can check it. If they want
a check anyway, the honest shape is their own §B-style info line (a `.git` is present in a
clone and absent in a tarball, so it can inform but cannot gate).
