## 2. Findings

### F1 — D1 is answerable now, by hash, and the answer is `61f77aa`

The globe's `main` tip carries `port/` bytes that are *self-consistent* (each file's sha256 equals
its own `PORT.json` entry) and equal to the hashes the handoff recorded (`ee43f647`-era). So the
rule D1 states ("copy from the revision whose `port/` bytes match a self-consistent globe
`PORT.json`; if the codec has moved past `ee43f647`, treat it as a new handoff") resolves today:
**`61f77aa` is a valid handoff revision, and the fixture identities in the plan are correct as
written.** Recommendation: record `61f77aa` (and the two file hashes) in §0/§4 as the revision to
fetch, and keep the "hashes are the authority" rule exactly as written — it is what makes this
safe when `main` moves again.

### F2 — the fixture round trip's gates can be pre-verified before anything under `port/` moves

All four of §4's handoff expectations check out offline (§1). Recommendation: add **B0** to the
plan — fetch the two artifacts from the recorded revision into a scratch directory, verify the two
sha256s, the two fixture identities, and `encode(decode(text)) === text`, and paste the results
into the worklog — *before* the port bump begins. Then B1's "If the fetched bytes differ, stop"
aborts before any repo state changes, and B5's identities are a comparison against a recorded
value rather than a hope. Cost: a few minutes and no repo edits.

### F3 — Phase B as written is blocked on globe 0.8.2 for its bundle half; split it

§4's B3 requires every regenerated bundle to go through the globe's 0.8.2 CLI *or* the handoff
command lines it records, and §0's precondition names 0.8.0–0.8.2 as the handoff. Measured: the
cutter (0.8.1) has landed, the bake CLI (0.8.2) has **not**. So today's executable branch of B3 is
"retire", not "regenerate" — and the plan's own acceptance ("no v1 artifact remains in shipped
bundles") is met by retiring them. Recommendation, in the plan's own style:

- **B-a — the port bump**: B1 + B2 + B4 (+B6). One series touching `port/`: the v2 codec and
  fixture in, the v2 manifest in, every reader on the single v2 `decode`, every writer on
  `make → fill → seal → encode`, the three `js/data/section-*.js` bundles **retired** (removed from
  `columns.html` and `SECTION_PACKS`), `experiments/port-check.js` rewritten to the v2 manifest, the
  D2 relocation landed, and D6's schema ambiguities returned. Executable today; ships no v1
  artifact.
- **B-b — the bundle restore**: B3's regeneration branch, gated on a v2 writer existing (the
  globe's 0.8.2 CLI, or an explicitly recorded hand-run 0.8.1 export). Each restored bundle carries
  the revision, exact command line, license and both identities, as B3 says.

This keeps the one-bump rule (nothing but B-a touches `port/`), removes a false dependency, and
keeps the retire/regenerate decision per-bundle where the plan already put it. It also makes the
"ships no v1 artifact" claim a B-a gate instead of a B-a/B-b hybrid.

### F4 — say what "one decode entry" means, because v2's `decode` takes text

A2's "single internal `decodePack(rawObjectOrText)`" hides the one API fact that would otherwise
grow a shim in B4: v2's `decode(text)` accepts JSON **text** only, while the v2 `verify(object)`
takes a parsed object. Recommendation: make the entry `decodePack(text)`, and let the
already-parsed-object path (`SectionPack.loadPack`, a `SECTION_PACKS` bundle object) call
`verify(raw)` and then `decode(JSON.stringify(raw))`. Also worth recording in A2's inventory, as
B4's checklist, the v1→v2 method map:

| v1 use | v2 route |
| --- | --- |
| `make` → fill → `quantize` → checksum | `make` → fill → **`seal`** (quantisation + checksum) → `encode` |
| `normalize(pack)` | **gone** — validation refuses instead of coercing (upstream §4.3) |
| `quantize(pack)` | **gone** — `seal` owns it |
| `validate(pack)`, `verify(pack)`, `checksum(pack)` | same names, same roles |
| `encode(pack)`, `decode(text)` | same names; `decode` still text-only |
| `edgeCode`, `arcKmBetween`, `latLonAt`, … | kept; new: `validateRaw`, `pathChecksum`, `hostCode`, `edgePolarity`, `setGap`, `circleThrough`, `polylineArc`, `directionAt`, `tangentAt`, `azimuthBetween` |

### F5 — D2: relocate the two deposit ports to `js/data/`, don't special-case `port/`

`experiments/port-check.js` §C asserts *directory = manifest* — the one-line invariant that makes
`port/` trustworthy. Listing non-shared files in `port/` (`site/`-style) breaks exactly that. Both
files are ordinary page modules already (`columns.html` script tags 132–133, consumed by
`js/deposit-core.js` / `js/deposits.js`), so the recommendation in the plan — option (a) — is the
right one: move them to `js/data/` in the B-a series, update page load order, `smoke.js` green,
values frozen (boundary 4). No catalogue is backported in either direction.

### F6 — bank the fixture state hash during A2, not during B4

A2's gate is "identical section state hash for the fixture pack before/after the refactor". Make
that a *recorded* number: print/assert the fixture section state hash from the pre-refactor tree
into the A2 worklog, so B4 compares against a banked value rather than against a remembered
observation.

### F7 — §0's pins need re-recording at execution (the plan already says so)

The plan's §0 names this repository `5fef1fb`; at this review the tree is `369ce20` (0.3.2 M2
landed) and the globe's `main` is `61f77aa`. The §0 rule stands — re-verify at execution start —
and F2's B0 is the concrete way to do it.
