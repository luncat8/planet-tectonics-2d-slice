# 0.4.0 — Plan: `index.html` is the shell, and one instrument contract

`index.html` was left behind `particles.html`: it has no transport buttons, no quality ladder,
no overlay bus, no ledger lines and no way to save a run, while the particle page has all of
them and the fixtures that guard them. This plan makes `index.html` the shell every later
release needs (0.5 pastes a transect into it, 0.9 adds the map and the globe to it), gives both
engines one instrument vocabulary, and files the captures that make a bug report reproducible.
It changes pages, wiring and the boot path. It does not add physics: the eruptive box and the
deposits stay in `0.2.0-plan.md`, the melt pipeline stays in `0.3.0-p3-plan.md`.

Contracts C1..C8 of `roadmap.md` §4 apply throughout.

## 1. What a page here must have

The table is the review of both pages at 25daf36. "column" is `index.html`, "particle" is
`particles.html`.

| capability | particle | column | required |
|------------|----------|--------|----------|
| clock slider, 0 = pause | yes | yes (two sliders) | yes |
| pause / step / reset / new planet buttons | yes | no | yes |
| keyboard transport (`space . r n`) | yes | `space`, `m`, `g`, `1-4` only | yes |
| quality / resolution switch | yes (`1/2/3`) | no | yes |
| camera presets as a radio group | yes (lid/deep/mantle) | yes (def/ovw/cru/bas) | yes |
| overlay switches with `aria-pressed` | yes (5) | 1 (`mesh`) + a checkbox | yes |
| overlay state read back from the renderer | yes | yes | yes |
| a rebuild is a new world, stated in the UI | yes | n/a | yes |
| HUD with a clock on line 1 | yes | yes | yes |
| HUD with a ledger | yes (mass, enthalpy, wall flux) | partial (melt only) | yes |
| a copyable capture of the current run | no | no | yes |
| save / load a world | no | no | column now, particle after P3 |
| URL prefill of a capture | no | no | yes |
| engine starts only when the page says so | no | no | yes |
| one global per file (C1) | no | no | yes |

## 2. The shell

### 2.1 Document structure

`index.html` keeps its name and becomes:

```
	<header id="nav">  column | particle | (map, 0.9)   </header>
	<main>
	  <section id="view-col" data-engine="col" data-prefix="col" hidden>  bar, stage, help </section>
	  <section id="view-pt"  data-engine="pt"  data-prefix="pt"  hidden>  bar, stage, help </section>
	</main>
```

One engine runs at a time. `location.hash` (`#col`, `#pt`) picks the view; `#pt` is the same
view the standalone page shows. `particles.html` stays in the tree and stays loadable: it is the
particle engine's page and `experiments/pt-ui.js` reads it. It includes `js/shell.js` and the
same view markup for one engine, so the shell has one implementation and the page is a
one-view instance of it. `README.md` (new) carries the page map and the harness commands.

### 2.2 Ids and the DOM contract (C2)

Elements are prefixed: `col-c`, `col-hud`, `col-sClock`, `pt-bMark`, ... Each engine's ui file
holds one table and one lookup helper:

```
	IDS: ['c', 'hud', 'sClock', 'vClock', 'bPause', ...],
	el: function (name) { return document.getElementById(PREFIX + '-' + name); }
```

and reads `PREFIX` from its own `<section data-prefix>`. The markup carries the prefixed ids and
`data-overlay` / `data-preset` attributes (2.6, 3.4). The harnesses keep reading the pages:
`pt-ui.js` already derives ids and buttons from the HTML, so it survives the rename once its
hardcoded `attrsIn('bMark')` calls become `attrsIn(PREFIX + '-bMark')`, and one check changes
meaning: "particles.html loads every `js/pt/*.js` exactly once" becomes "every `js/pt/*.js`
exactly once, plus `js/shell.js`". `smoke.js` gets the same treatment for `index.html`.

### 2.3 Boot (C1, and no self-start)

Every engine file becomes an IIFE that creates exactly one global:

```
	(function () {
	'use strict';
	... file body, unchanged ...
	if (typeof module !== 'undefined' && module.exports) module.exports = P;
	else window.PTP = P;
	})();
```

The names exported are the ones already in use (`PTP PTS PTG PTF PTSC PTRNDR PTUI PTR`) plus
new column-engine names (`COLP COLS COLGEO COLCOL COLMNT COLSLAB COLPLT COLMAG COLCRU COLSURF
COLRNDR COLUI COLSIM`). Note the two real collisions this removes: `js/pt/state.js` and
`js/pt/sim.js` assign the particle state to a top-level `var S`, and every column-engine file
reads a top-level `P` and `S`; today the second engine loaded silently rewrites `window.P` and
`window.S` for the first one.

`js/perf.js` is the one deliberately shared file (`0.3.0-plan.md` §12): both pages load it and
both engines read the same smoothed laps, so it exports exactly one global, `window.PERF`, from
its IIFE. `js/rng.js` is the column engine's own stream and exports `window.RNG` the same way.
No other file is shared between the engines.

No engine starts itself. `js/sim.js` and `js/pt/sim.js` lose their `document`-guarded tails and
expose `start(host)`:

```
	COLSIM.start({ canvas: 'col-c', hud: 'col-hud', bar: 'col-bar' });
```

`js/shell.js` (loaded last, by both pages) finds the sections, shows the one named by
`location.hash`, and calls that engine's `start()` exactly once, on first activation, so a
switch never leaves a second rAF loop running. Switching away calls `stop()`: cancel the frame,
detach listeners, keep the state, so returning to a view resumes the same world instead of
rebuilding it. (0.7 relaxes exactly this for the synced pair — the inactive view keeps stepping
and skips only its render — and it says so where the sync protocol is defined.)

### 2.4 Chrome

`style.css` (new) holds what both pages duplicate today: `body`, `button` and the single lit
rule `button[aria-pressed="true"]`, `canvas`, `#hud`, `#help`, the bar/fieldset layout. Engine
specifics stay in the page (`#stage`'s grid for the column camera, the particle bar's groups).
Deliberately not a framework: three class names and the toggle rule.

## 3. The instrument vocabulary

### 3.1 Transport

Buttons `pause | step | reset | new planet` and keys `space . r n` behave identically in both
engines:

- pause sets both clock sliders to 0 and remembers their values, so a resume restores the exact
  rates (the column engine has two clocks, so it remembers a pair);
- step is pause + one frame, and it also works while a run is playing;
- reset rebuilds the same seed at the current settings;
- new planet takes the next seed and resets, and it is the only transport that changes
  `P.seed`; the seed field (new) shows and accepts it.

### 3.2 Clocks

Both pages keep the convention "slider at 0 is pause; the slider is log over its range". The
column engine keeps its two clocks and labels them `plates` and `lava`; the particle engine has
one and labels it `geology`. Every readout is `kyr/f`, `Myr/f`, `min/f` or `h/f` with the unit
attached, never a bare number. The HUD's first line always carries absolute `t` in Myr.

### 3.3 Quality and rebuilds

The particle engine's quality ladder (mesh + markers per node) is the model:

| engine | levels | what changes | cost |
|--------|--------|--------------|------|
| particle | `1/2/3` = 256x24, 512x48, 1024x96 | mesh and markers/node; the population and physics constants do not | measured, in the HUD |
| column | `1/2/3` = (nCols, nRows, colCap) triples | columns, fan rows, capacity | measured by a new `experiments/qual-bench.js` |

The column ladder's numbers are not chosen here: `qual-bench.js` measures frame cost, memory
and the fan's heat ledger at each rung and the plan's default is the cheapest rung inside the
existing 6 ms body budget. A level change is a **world rebuild**: the state is not carried, the
button says `quality 2/3 · rebuild`, and the capture records the level so the run can be
repeated. (A live regrid is the map engine's 0.7.0 problem and is out of scope here.)

### 3.4 Presets

One vocabulary, four names, each engine mapping its own stops onto them:

| stop | key | column | particle |
|------|-----|--------|----------|
| overview | 1 | `ovw` (the whole depth) | `mantle` (whole box) |
| crust | 2 | `cru` x10 | `lid` |
| section | 3 | `def` | `deep` |
| basin | 4 | `bas` x40 | `surf` (a new shallow stop: the top 150 km) |

The buttons stay in the markup with `data-preset="overview"` and their initial `aria-pressed`;
the ui builds the group from the markup and lights it from the camera's own `presetName`, the
existing single-writer rule. Any manual pan, zoom or axis move unlights the group, as both
engines already do.

### 3.5 The overlay bus

A switch button carries `data-overlay="mesh"`; the renderer owns a flat flag table
(`COLRNDR.flags`, `PTR.flags`) whose entries are `{key, label, key, def}`. The ui wires every
`data-overlay` button in the markup to its flag and lights it from the flag, and the keyboard
map is that table's `key` column, so an overlay cannot exist without being wired, lit,
keyboard-reachable and documented in the help line. The markup still ships the initial
`aria-pressed` (the fixture asserts it) and the fixture's job becomes mechanical: for every
`data-overlay` button, the markup's state equals the renderer's flag at load.

This replaces the two hand-maintained lists (`PTUI.TOGGLES`, `PTUI.KEY_TOGGLE`) and makes the
column engine's future overlays (ore potentials, deposits, vents, loads) one line each in the
markup plus one flag in the renderer, which is how `0.2.0-plan.md` M2/M3 should land.

### 3.6 The HUD field set

One order for both engines, so the two pages read the same way and 0.9 can merge them:

1. identity — `t` (Myr), clock rate, seed, quality, and the state hash when `h` is held;
2. rate — fps, sim ms, draw ms, and the engine's own rate number (px/frame for particles,
   fastest plate in cm/yr for the column engine);
3. population — counts against capacity for every entity the engine has;
4. ledger — mass and, where the engine has one, enthalpy, in one line with the wall flux and
   the closure residual (C6);
5. invariants — the assertions the engine can check at 2 Hz (sorted columns, min gap, plate
   census, marker/grid coverage);
6. probe — last, and only while the pointer is in the canvas.

Rebuilt at 2 Hz, never per frame, and the string is built in one function per engine (both
already do this; the plan fixes the order and the units).

### 3.7 The capture

A `capture` button copies a text block; `?seed=7&dt=50&qual=2` prefills the same settings from
the URL, which is what makes a capture a reproduction rather than a description:

```
	capture 0.4.0
	page column
	engine column 0.2.x
	seed 7
	settings qual=2 nCols=512 nRows=64 dt=50000 yr/f erupt=1800 s/f eventCadence=1
	state t=123.456 myr frame=2469 hash=0x1a2b3c4d
	pack none
```

Rules: every field is written with its unit; every non-default setting is present (the map
engine's convention); the hash is the engine's own state hash; `pack` carries the transect
fold and line once 0.5 lands; unknown URL keys are listed on the HUD's first line so a typo is
visible instead of silent.

## 4. Milestones

### M0 — one global per file (C1)

Wrap every file of both engines, rename the exported globals as in §2.3, update the harnesses
that name them (`smoke.js`, `pt-ui.js`, `pt-check.js` and the `experiments/pt-*.js` set load
files through `require` and are unaffected except where they read the page's globals).

Gate `experiments/globals.js` (new):

- loading every script of both engines, in page order, into one vm context with the DOM stub
  defines exactly the documented global list and nothing else;
- step the column engine 200 frames, then load the particle engine and step it 200 frames,
  then step the column engine again: `S.hash()` and `PTS.hash()` both match their recorded
  golden values, and a table of sampled fields shows the first engine's parameters unchanged
  (`COLP.nCols`, `COLP.sl.g`, ...) after the second engine loaded;
- both engines can be constructed and stepped in either load order.

### M1 — the shell

`style.css`, `js/shell.js`, the two view sections, id prefixes and the ids tables, `README.md`.
`particles.html` becomes the one-view instance. Gate: `pt-ui.js` and `smoke.js` green after
their id updates, both pages open, `#pt` and `#col` switch, and a switch away and back resumes
the same world (hash unchanged, frame counter continues).

### M2 — transport and clocks

Buttons and keys of §3.1, the remembered-rate pause, the seed field, the two-clock labels.

### M3 — quality

The column ladder with `qual-bench.js`; the particle ladder keeps its numbers and gains the
rebuild wording; the HUD's cost line reports the level's measured ms/frame.

### M4 — presets and the overlay bus

§3.4 and §3.5. Gate: the parity fixture of M7 checks that every `data-overlay` button in the
markup matches its renderer flag at load, and that every entry of the renderer's flag table
exists in the markup.

### M5 — HUD and capture

§3.6 and §3.7. Gate: `experiments/ui-parity.js` asserts the field order and the units on both
pages; a capture from each page parses with the capture grammar and reproduces the same
settings, seed and hash when prefilled.

### M6 — captures on disk

- Column engine: `SAVE`/`LOAD` over every typed array and scalar in `S` plus `P.seed` and the
  sliders. Binary, little-endian, magic `PT2D` + a version word; a header carries the version,
  seed, `colCap`, `layerCap`, `nRows`, `nCols` and the field table, so a mismatch is an error
  with the expected and the found value in the message; everything is validated before live
  state is touched, and a failed load leaves the running world alone. This is `0.2.0-plan.md`
  M4's deliverable, re-homed here because it is a page feature and the 0.2.x kernels do not
  need it first.
- Particle engine: the same shape, after P3 freezes the pool's fields
  (`0.3.0-p3-plan.md` §1.3 and the addendum). The version word is the only compatibility
  contract.
- Both: a `Load` file input, a `Save` download, and the gate "save, reset, load, run 1000
  frames: the hash equals the uninterrupted run's".

### M7 — acceptance and the parity fixture

`experiments/ui-parity.js` (new) parses both pages and asserts the shared contract: the id
prefix rule, one `<section data-engine>` per engine, the transport buttons and keys, the
`data-overlay`/`data-preset` wiring, the HUD field order, the capture grammar, one global per
file (by scanning for top-level `var`/`function` outside IIFEs is not possible in a regex, so
the fixture loads both engines into one sandbox and diffs the global list), and that
`particles.html` and `index.html` agree on the vocabulary names.

## 6. Acceptance

1. `index.html` opens from `file://`, shows the column view, and every control in §1 works with
   keyboard and mouse; `#pt` switches to the particle view and back without rebuilding either
   world.
2. Both engines are present in one page and neither one's parameters, state or renderer flags
   change when the other is loaded, constructed or stepped (the `globals.js` evidence).
3. Every overlay button, preset button and transport button is lit exactly when its own
   renderer flag says so, after a click, after its key, and after a manual camera move.
4. A capture copied from either page, pasted into the URL, reproduces the same seed, settings
   and world; a saved world reloads and continues bit-identically for 1000 frames.
5. Every existing fixture (`smoke.js`, `pt-ui.js`, `pt-check.js`, `pt-crust.js`, `pt-drift.js`,
   `pt-surface.js`, `pt-wrap.js`, `pt-band.js`) is green, with only the id/global updates
   this plan names.
6. The frame budget is unchanged where the physics is unchanged: the particle engine's shipped
   configuration stays inside its 14 ms gate, and the column engine's body pass stays inside
   6 ms at the shipped quality.

## 7. Risks

- **The IIFE pass touches every file while 0.3.0-P3 is being written.** Mitigation: M0 lands
  before P3's first kernel file; the rule is stated in the P3 plan's addendum; the golden
  hashes catch a silent behaviour change better than review does.
- **The id rename touches working fixtures.** The fixtures are the reason the rename is safe:
  they read the page, so a missed id fails immediately and loudly.
- **Quality ladders invite regressions.** The column ladder's default is the shipped rung until
  `qual-bench.js` says otherwise; the particle ladder is untouched.
- **The shell tempts a third engine.** The particle view is a view of the same shell, not a
  second copy of the particle page: one implementation, and `particles.html` is that shell with
  one section. If the two ever diverge, the parity fixture fails.

## 8. What this plan does not do

- no new physics, no ore kernel, no eruptive box (0.2.0), no melt pipeline (P3);
- no live regrid between quality levels;
- no map view, no transect import (0.5/0.6) beyond the panel slots this shell reserves;
- no WebGPU, no workers, no build step: C7 stands.
