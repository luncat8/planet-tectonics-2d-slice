# 0.9.0 — Plan: one page, three views

The target: one `file://` document that shows the globe, the top-view map and one cross-section,
running together on one clock, with the section's line drawn on the globe and the map. The map
engine of `planet-geotectonics` is vendored as a pinned library; this repository's column engine
is the section; the shell, the exchange codec and the ledgers are what hold them together.

Contracts C1..C8 of `roadmap.md` §4 and the ownership table of §5 apply. 0.4-0.7 are the
prerequisites: the shell and the ids (0.4), the pack (0.5), the reconstruction (0.6) and the sync
protocol with its reconciliation ledger (0.7).

## 1. What "integrated globe" means concretely

- **The globe is the map engine's 3D view**, not a new renderer: its displaced icosphere /
  heightmap lattice with the translucent sea shell, the orbit camera and the displacement
  control, exactly as `0.5.0-plan-3d-render.md` there describes. This plan adds the **cut
  plane**: the section's great circle drawn on the globe surface, and a quad strip on the
  circle's plane carrying the section's own colours down to the drawn depth.
- **The top view is the map engine's 2D map**, its layer list and its probe, with one addition:
  the current line, drawn as a great circle, moveable by dragging its two endpoints.
- **The section is this repository's column engine**, fed by the sync protocol of 0.7 and drawn
  by its own renderer.
- **One clock.** The map's `t` is the master (roadmap §5); the globe renders the map's state; the
  section follows with its lag reported.
- **One capture** covering all three: the map's seed/level/settings, the section's pack fold and
  mapping version, the line, and each engine's state hash.

The integrated page is a **view** of one planet, not a coupling of two simulations: the physics
authority does not change (roadmap §5). What changes for a viewer is that the section's line is
visibly a cut through the same world they are looking at.

## 2. The library merge

### 2.1 Layout

| directory | content | owned by |
|-----------|---------|----------|
| `js/` | this repository's column engine, unchanged in place | this project |
| `js/pt/` | the particle engine, unchanged in place | this project |
| `js/map/` | the vendored map engine (its `js/*.js` subset + its `vendor/`), unmodified | `planet-geotectonics` |
| `js/slicepack.js`, `js/slice.js`, `js/sync.js`, `js/shell.js` | the exchange, the reconstruction, the protocol, the page | this project |
| `js/map-adapter.js` | the only code that names the map engine's API | this project |

The existing trees are **not** moved: `js/*.js` stays where it is, because every fixture, every
plan reference and every archived log here points at it, and moving files buys tidiness that the
shell already provides. The particle engine keeps `particles.html` and stays a view.

### 2.2 The pin

- `js/map/PIN` records the upstream repository, the commit, the upstream version string, the
  copy date and the file list with a checksum per file.
- `tools/map-sync.js` (node, not loaded by any page) copies the upstream subset into `js/map/`
  from a local checkout passed as an argument, rewrites `PIN`, and refuses to run if the
  checkout's `git status` is dirty or its commit does not match the argument.
- `experiments/vendor-check.js` re-computes every checksum and fails on any difference: a local
  edit to a vendored file is a build error, not a convenience.
- **Nothing local patches a vendored file.** A change the map engine needs is either made
  upstream and picked up by a pin bump, or expressed in `js/map-adapter.js`. If a view needs a
  hook the upstream engine does not offer (for example, a callback when its raster finishes for
  a frame), the adapter provides it by wrapping the engine's own public entry points, not by
  editing it.
- `js/map/NOTICE.md` records the source, the commit, the MIT licence header and the fact that the
  files are unmodified. Both projects are MIT (`luncat8`, 2026).

### 2.3 What is vendored, and what is not

Vendored: the engine's `js/*.js` (state, columns, contact, surfaces, plates, events, mantle,
render, render3d, water, checkpoint, extract, ui-facing helpers) and its `vendor/`.
Not vendored: its Earth data packs (`js/data/*`, 6.2 MB) and its 9.7 MB `data/` directory — the
integration is about a procedural planet with a line on it, and an Earth start can be a later,
explicit addition with its own size decision. The map engine's own probes of an absent pack must
degrade to "not available" rather than throw.

## 3. The three views

### 3.1 The document

```
	<header id="nav">  globe | map | section | (particles)      one clock, one transport  </header>
	<main>
	  <section data-engine="map"   data-prefix="map" ...>  the globe canvas OR the map canvas </section>
	  <section data-engine="col"   data-prefix="col" ...>  the section </section>
	  <section data-engine="pt"    data-prefix="pt"  ...>  the particle view (optional) </section>
	</main>
```

The globe and the top view are **two renderers of one engine**, so they share a section and a
radio (`3D | map`), exactly the way the map project's own page already switches. Only one of the
three is visible at a time; the engines all step.

### 3.2 The cut plane on the globe

- Geometry: `js/map-adapter.js` maps the line (A, B on the unit sphere) to a quad strip: `2 x K`
  vertices along the great circle on the sphere surface, and the same vertices at the drawn depth
  (`-depth`) scaled by the globe's own displacement convention. `K` is fixed (e.g., 128) and
  preallocated; the strip is rebuilt only when the line or the map's mesh changes, never per
  frame.
- Texture: the section's own column colours are sampled into a 1D strip (`K x 1`) once per sync
  import from the section's state, and the quad's vertical coordinate samples that strip. The
  section renderer already owns the palette; the cut plane reuses it so the two views agree.
- The surface trace of the line is drawn as a bright arc on the terrain, and the two endpoints
  as markers with their latitude/longitude.
- A `Cut` overlay switch (the 0.4 overlay bus) shows and hides the plane; the plane's depth
  window is the section's own drawn window, so the cut never claims more than the section shows.

### 3.3 Picking the line

- On the globe: click sets A, a second click sets B, both clamped to the visible hemisphere; the
  line follows the drag of either marker and re-imports at the next cadence (0.7 §4).
- On the map: the same two clicks in map coordinates, converted to the unit sphere by the map
  engine's own view mapping (the picker of `0.5.0-plan.md` M3 does exactly this).
- Refusals: equal or antipodal picks (no unique great circle), and a pick in an uncovered cell
  (`owner < 0`) is refused with the same reason the exporter gives, so the picker here and the
  exporter there speak one language.
- Snapping aids (the physical fix for the dropped normal velocity, 0.6 §12): snap the line
  perpendicular to the nearest boundary at the picked point, or along the local plate motion.
  Both are display-side computations of the same fields the pack exports; neither changes the
  pack.

### 3.4 The control bar

One clock (the map's), one transport (play/pause/step/reset; reset rebuilds the map and re-imports
the current line), one seed, one quality list that names each engine's own level (the map's L5/L6,
the section's column count, the globe's mesh), and the synced section's transport shown disabled
while synced. The overlay bus collects the three renderers' flags with the engine name as a
prefix (`map-...`, `col-...`, `pt-...`), so one bar drives everything and nothing is duplicated.

## 4. The observation log (the return path)

The section returns one thing to the map: a **core log** for the cells the line crosses. It is an
observation, not a physical field (roadmap §5), and the map treats it as such.

- Format: the same codec discipline as the pack (`CORE1`, a name-keyed field list, a fold), one
  record per section column: the map cell, the column's provenance, the bed list (lithology,
  thickness, age, flags), the divergence number from 0.7 §4.2, and the section's epoch.
- Cadence: at the sync cadence, and only for columns whose `diverged` fraction changed beyond a
  threshold — a log every import for every column is a data leak with no reader.
- The map stores them in a fixed-capacity side table keyed by cell (`coreCap`, a new capacity in
  its own params), validated before acceptance: the bed thicknesses must sum to the log's own
  total, the ages must be monotone, the cell must exist. A rejected log is reported to the
  section's panel and counted; it never enters the map's state.
- The map shows a log in its probe and inspector beside its own modelled thicknesses, labelled
  `observed (section)` with the divergence number, so a reader can see both numbers and their
  difference. This is exactly the material the map project's 0.6.1 prospector wants for synthetic
  core logs, which is why the return path is a feature of both projects rather than a private
  convenience of this one.
- The map's physics cannot read the table. Its kernels have no reference to it, and the
  determinism fixture of the map project (its state hash) is unaffected by an accepted log —
  that is the test that keeps the observation on the observation side.

## 5. Performance

- Budgets are measured, not promised. The 0.9 page runs three renderers and two stepping
  engines; only the visible view draws, so the page's frame is the map's step plus the section's
  step plus one render.
- The map's own README is the authority on its cost: the CPU path is calibrated at L5 and L6/L7
  are the WebGPU path. The integrated page's default is therefore the map at L5 on the CPU, the
  globe as the map's own 3D renderer, and the section at its shipped quality.
- If the triple view does not fit the frame on a given machine, the policy is stated and
  automatic: render the globe every other frame (a `frame skip` reported in the HUD), then drop
  the section's column count one quality step, then stretch the sync cadence. The physics never
  changes to make a frame, and the HUD always says which of these is active.
- The `solo` mode of the shell (one view) remains available, and it is the mode used for the
  recorded acceptance run's screenshots.

## 6. Milestones

### M0 — the vendored library

`tools/map-sync.js`, `js/map/PIN`, `js/map/NOTICE.md`, `js/map-adapter.js`, the vendored subset,
and `experiments/vendor-check.js`. Gate: the adapter starts the map engine headlessly in a DOM
stub, steps it, reads its raster and stops it; the vendor check passes; a deliberately edited
vendored file fails the check.

### M1 — two engines, one page

The shell hosts the map view and the section view, one clock, the transport, the capture covering
both. Gate: `experiments/page09.js` (extended from `ui-parity.js`) starts both, steps both, and
asserts one clock, one capture grammar and no global collisions (the 0.4 `globals.js` list grows
by exactly the map engine's names).

### M2 — the cut plane

§3.2 and §3.3. Gate `experiments/cutplane.js`: the great circle and the strip's vertices against
hand-computed values for the equator, a meridian and an oblique line; the degenerate picks
refused; the strip rebuilt only on a line or mesh change.

### M3 — the picker in the page

Line picking on the map and the globe, the snapping aids, the refusal messages, and the line's
propagation into the next import. Gate: a DOM-stub run that picks, moves, snaps and re-imports,
with the section's provenance updated.

### M4 — the observation log

§4, including the map-side table and validation, the adapter's API, the inspector display and the
map's determinism fixture run with a log accepted. Gate `experiments/core-log.js`.

### M5 — performance and the acceptance minute

The measured triple-view frame at the shipped settings, the automatic degradation policy, and the
recorded acceptance run of §7.

## 7. Acceptance — the recorded minute

One `file://` page, one click to start, and for one wall-clock minute at the map's default
cadence a viewer sees:

1. the globe turning with the plates, the sea shell, and the cut plane standing on the line;
2. the map view of the same state, with the line and its endpoints, and the plate/boundary layers
   switching as they do in the map project today;
3. the section below, tracking the map's epoch, its stratigraphy and its own ledgers on screen,
   with the modelled-material hatch under the Moho and the reconciled/diverged fractions;
4. a rift or a boundary crossing the line, and the section's columns under it changing at the
   next import — the same event visible in all three views;
5. a stop, a capture, and a restart from the capture that reproduces the same seed, line, level,
   settings and (with the same step sequence) the same hashes.

The run is recorded in `archive/0.9.0-worklog.md` with the frame measurements, the settings, the
capture text, the packs used and the reconciliation ledger.

## 9. Risk register

- **Upstream drift.** The pin, the checksums and the adapter contain it: an upstream change is a
  deliberate pin bump with the cross fixtures re-recorded, never a surprise. If the map project's
  needs and this one's diverge, the adapter is where the difference lives.
- **Three renderers, one frame.** The degradation policy of §5 is stated before it is needed, and
  each step of it is visible in the HUD; the fallback (the map's own page plus a file-based sync,
  0.7 option A) keeps every rule of §4 and §5 of the roadmap intact if the merge proves too
  heavy on a given machine.
- **Two clocks again.** The 0.7 rule (the map is master, the section reports its lag) is the only
  clock relationship allowed. A feature that needs the section ahead of the map needs a plan
  change, not a flag.
- **The observation log becoming physics.** The map's kernels never see the table, and its
  determinism fixture is run with a log accepted. If a future feature wants to read it in a
  kernel, that is a physics change with its own plan.
- **Scope.** The particle engine is not a fourth view here; its page and its plans stay as they
  are. The vendored engine's Earth packs are not vendored; an Earth start in the integrated page
  is a separate size and licence decision.

## 10. What 0.9 does not close

- Live resolution change inside the map engine (its own 0.7.0) and the WebGPU section engine (not
  planned): the integrated page reads whichever engine the map project ships.
- A spherical section solver: the cut is drawn on a sphere and simulated on the flattened strip,
  with the error stated (0.6 §1).
- Any physics coupling beyond the observation log.
