# 0.4.0 — Plan: sync and feature exchange with planet-geotectonics

This plan says what the slice exchanges with its reference project, in which direction, under
which contracts, and in which order. It covers the second item of the draft's `>0.3` block
("sync/exchange features with base project") and it is the prerequisite for the third
(a slice drawn on the top-view map, targeted at 0.9).

Pointer: `https://github.com/luncat8/planet-geotectonics`, **main @ d909476 (0.6.1)** is the
commit this plan was written against. Every port below names that commit until it is bumped.
The counterpart has the same AGENTS.md conventions but a much larger surface: a global
simulation with real Earth packs, deposits and prospecting, a checkpoint format, a 3D view and
a WebGPU twin.

## 0. Where the two projects stand

| | planet-geotectonics | this repository |
| --- | --- | --- |
| dimension | sphere (icosahedral dual-hex, L5–L8) | 2D section, periodic line (column engine: 2π·6371 km, particle engine: 16 000 km) |
| state | Lagrangian columns in rigid plate frames, quaternions | same idea, 1D: layer stacks per column (column engine); markers + grid (particle engine) |
| time | 10–100 kyr steps, dt-insensitive kernels | same for geology, plus a wall-clock eruption clock (column engine) and a demo clock (particle engine) |
| depth | one column = one cell, aggregate thicknesses | depth-resolved beds, log (asinh) depth scale |
| maturity | 0.6.1: deposits, prospecting, economics, Earth packs, 3D, WebGPU | 0.3.0: particle engine at P2.3; column engine at 0.1.6 (forces and ledger gated, the collision fixture is still open) plus the 0.2.0 eruptive and deposit work; no save/load |
| harness | `tests/*.js`, `node tests/run-all.js` short/full/release (46 files) | `experiments/*.js`, one script per check, no runner |
| release gates | owner-rig full/release profiles, GPU parity ensembles | measured fixtures per milestone, logs in `experiments/logs/` |

The relationship today is **unrecorded copying**. The column engine is a deliberate 1D
adaptation of the reference's design (`0.1.0-design.md` §1, §4, §9: the six ore potentials,
`kV kM kM2 kA kRec kO kB kB2 kDecay`, the damage corridor, the 3×3 force balance reduced to a
mean, reference §7.3 sediment routing). Those ports carry no upstream commit, no diff note and
no drift check, and the reference has moved on since. The particle engine has no counterpart
there at all.

Two consequences drive the whole plan:

1. **A reference that moves is not a specification.** Constants copied in 0.1.x are now
   indistinguishable from constants chosen here; for example the arc-crust law is the same
   shape in both repositories (`kArc · Tm · rate · dt`) but the constant is 65 upstream and
   8e3 here because this side divides by `vRef` — a difference that must be recorded, not
   guessed at.
2. **The exchange is not symmetric.** The slice needs the reference's mature geology
   (deposits, water, Earth data, checkpoint); the reference needs the slice's vertical
   resolution, its section view and (later) its emergent-particle solid.

## 1. Rules of exchange

### 1.1 One owner per concept

| Concept | Owner | Why |
| --- | --- | --- |
| globe geometry, grid, Euler poles, Earth packs, prescribed kinematics | geotectonics | it has the packs, the rotation model and the scores |
| deposit generator core, priors, economics, instruments | geotectonics | versioned there, fitted to USGS priors there |
| water level / eustasy, hypsometry | geotectonics | display-only module, already shared vocabulary |
| checkpoint envelope (header, version, padded blocks) | geotectonics | a format, not an implementation |
| capture header (`js/env.js`) and the runner/profile layout | geotectonics | it has the release-gate discipline |
| depth-resolved stratigraphy (beds, deposits by depth) | slice | 1D does this and 3D does not yet |
| section geometry, log depth scale, section renderer, camera presets | slice | built here |
| page-parsed load order in the headless harness | slice | derived from the page, not hand-maintained |
| emergent-particle solid (bonds, clusters, welding) | slice | research-stage; the globe carries a different representation |
| two-clock eruption presentation | slice | a display decision, not physics |

A concept has exactly one owner. The other repository may hold a port of it, never a second
source.

### 1.2 Four kinds of exchange

| Kind | Rule | Drift gate |
| --- | --- | --- |
| **shared-identical** | byte-identical file in both repositories; pure math, data or a format | sha256 in the manifest, asserted by a test on both sides |
| **adapted port** | a copy with a provenance header: upstream path, upstream commit, what changed and why | the header is reviewed at the port bump; the port names the fixture that reproduces upstream behaviour where the physics is 1D-reducible |
| **concept** | no code: the plan cites the upstream section, the local code is written independently | a line in the divergence table (§2.6) |
| **data pack** | generated file, never hand-edited, license and sources travel with it | format tag + checksum; the generator is the owner's tool |

Shared-identical is reserved for files that genuinely have no environment: `deposits.js`'s
hashing and draw core, `data/deposit-models.js`, `data/deposit-economics.js`, `water.js`,
`env.js`. Everything that touches a grid, a page or a state layout is an adapted port.

### 1.3 Provenance header

One line, first line of an adapted port, and the same line in the manifest:

```
// ported from planet-geotectonics @ d909476 js/contact.js §arc crust: same law, /vRef normalisation added
```

A file with no header is local code and may be changed freely. A file with a header is changed
only by a port bump (§8).

### 1.4 Manifest and check

`port/PORT.json` holds the pinned upstream commit, the shared files with their sha256, and the
adapted ports with their upstream paths. `experiments/port-check.js` asserts every shared file's
hash and that every port carries a header naming a commit in the manifest. The counterpart gets
the mirror check in its own test list. Neither check touches the network, so both work on
`file://` and in the sandbox.

### 1.5 Version bumps

Files that already carry their own version (`deposit-models.js`, `deposit-economics.js`) are
bumped upstream; this repository takes the bump wholesale and records it in the manifest. A
port bump (§8) is a commit that re-records upstream commits and hashes plus a one-line note of
what changed. Nothing else may touch a ported file.

### 1.6 Deliberate divergences (do not "fix")

| Divergence | Reason |
| --- | --- |
| the slice is a line, the globe is a sphere | 1D periodic box vs icosahedral grid; no flow through the section's ends |
| dt-insensitive 10–100 kyr kernels here vs a demo clock and wall-clock eruptions there | the particle engine exists to be watchable; the globe exists to be measurable. The second clock is a display layer and must never be mixed into a geologic rate |
| profile relief diffusion (`zh`) here vs material erosion/sediment there | `zh` is a smoothing proxy; the particle engine's P4 replaces it with real transports |
| diagnostic melt here (until P3) vs conserved melt there | stated in the HUD; no feedback claimed |
| meters (`z`) upstream, kilometres here | converted at the pack boundary, once, and recorded |

### 1.7 No new machinery

No submodules, no package manager, no build, no network at runtime. The exchange is files,
manifests and checks, exactly like the rest of both repositories.

### 2.2 E1 — capture header and settings prefill

Every log this repository writes should say which machine and build produced it, and every run
should be reproducible from a URL. Port `js/env.js` as a shared-identical file, print its line
at the top of each harness run and in the page HUD footer, and accept
`?seed=&dt=&mesh=&preset=` in `js/pt/ui.js` and `?seed=&geo=&erupt=` in `js/ui.js`, named after
the sliders. The upstream convention is that **a capture's header records every non-default
value**, so the URL in the header re-runs exactly what the log describes.

Gate: two runs with the same URL print the same header and the same state hash; the URL gained
from a modified run re-runs it.

### 2.3 E2 — a runner

One `experiments/run-all.js` with the upstream's shape: a short profile by default, `--full`
adding the long runs, a per-test time line and a non-zero exit on the first failure. The short
profile here is the four page/kernel checks plus the per-milestone `pt-*.js` and `*-check.js`
scripts that stay green.

### 2.4 E3 — checkpoint

The design declared save compatibility out of scope for 0.1/0.2 (`0.1.0-design.md` §10) and the
column engine has no serializer. Take the upstream envelope: 64-byte header, magic, version,
array count and byte total, then padded blocks — magic distinguishes a section blob from a
world blob (a slice-local magic, same layout). Port it as an adapted port: the header and the
padding rules are shared-identical in spirit, the record list is the slice's own.

Gate: save/load round-trips every typed array of both engines bit-identically (the state hash
already used by `pt-check.js` is the witness), a truncated or foreign blob is rejected by
header, and a version bump is refused rather than half-read.

### 2.5 E4/E5 — deposits and prospecting (the big one)

This is where the exchange pays for itself: the globe has a deterministic catalogue whose bodies
are a pure function of `(seed, generator version, snapshot checksum)`, and instruments with
honest, declared limits. The section analogue is natural — along-section distance `s` and depth
`y` replace latitude/longitude and depth.

Plan:

1. **Shared core.** Vendor the hashing/draw functions and the body model (`mix32`, `combine`,
   `drawCandidate`, the truncated normal, six-significant-digit rounding, the ellipsoid
   parameters) byte-identical with `deposits.js`'s header intact; a shared fixture
   (`fixtures/deposits-draws.json`) pins the draw sequence for a set of keys and both
   repositories assert it. That single fixture is what makes "the same body" mean the same
   thing in two projects.
2. **Priors and economics.** `data/deposit-models.js` and `data/deposit-economics.js` are
   shared-identical, including their `version` fields and `status: 'game'`. The slice inherits
   the upstream honesty rule: priors are game parameters until fitted, and ~19 % of bodies
   being scenario-positive is a property of the scenario, not a claim about Earth.
3. **The section snapshot.** A `snapshotSection(state)` mirroring the upstream
   `Deposits.snapshot`: blurred potentials (same six fields, same order, same blur), host
   class, altitude, thickness, age, and a checksum over the same quantities. Tiles are the
   section's own: `(seed, version, packChecksum, tileIndex, family, ordinal, drawIndex)`.
4. **The 3D → 2D reduction, declared.** A body is a 3D ellipsoid; the section sees one plane of
   it. Rules to write down before any code: the section's snapshot carries no out-of-plane
   coordinate, so a body's out-of-plane offset is folded into the projected support radius; a
   body whose out-of-plane offset exceeds its own radius is invisible to the section (it exists
   in the pack's 3D neighbourhood and not in this plane); drill and instrument footprints use
   along-section distance only. These are reductions, not equivalences, and the plan states
   them as such.
5. **Instruments.** Adapted ports with the reduction above. Visual/sample need exposure, drill
   intersects vertically, magnetic/EM and seismic keep their footprints in `s`. Null means not
   detected within support — never absent.

Gate: same key sequence → same draws as the upstream fixture; a section catalogue is identical
across click order, a whole-section scan and a re-import; every body round-trips through JSON
exactly; a survey of a pinned site yields only its own tiles; the ledger of discovered bodies
survives until the world is reset.

### 2.6 E6 — water level

`water.js` is display-only upstream and reduces cleanly to a line: `fromElevations(z, x)`
integrates `max(0, level - z)` over the section's columns, with "volume" read as **area per unit
out-of-plane width**. Level mode comes free; volume mode is the same solve with the section's own
datum.

Gate: for the same elevation array, the section's solved level equals `Water.fromElevations`
(shared fixture), is monotone in volume, and clamps at the module's own `ZLO`/`ZHI` as
`dry`/`flooded` rather than silently saturating.

### 2.7 E7 — erosion, sediment routing, accretionary prism

Both repositories implement the reference's one-hop erosion and routing, this one in `js/surface.js`
and `js/crust.js`. Before porting anything else, the audit in M2 must decide whether the existing
copies are current: the reference has an open data-quality increment (0.4.8) that changes what the
sediment and crustal-thickness fields are conditioned on, and its own plan warns that the
calibration points are not per-value measurements. The reconciliation is: one divergence table,
one mass-accounting fixture that closes, and a decision per concept — adopt upstream, keep local,
or declare a divergence.

### 2.8 E8 — Earth packs → the section pack (the 0.9 enabler)

The reference bakes real Earth packs (`tools/earth/bake_earth.py` → `js/data/earth-*.js`, 1° and
0.5°, 0–250 Ma, PALEOMAP rotations, CC-BY 4.0 with `SOURCES.md` and `License.txt`). The slice
should never load a 536 KB pack: it needs **one line's worth of it**. So the exchange is a new
generated artifact, `pgt-section-pack` (§4.1), baked on the globe's side and consumed here as a
small generated JS module.

Nothing in this milestone is a live link: a pack is a file, baked offline, checksummed, and
carried with its license.

### 2.9 E9/E10 — presentation and GPU (later)

Elevation ramps and the six ore hues must mean the same thing in the globe's map, the globe's 3D
view and the section, or a viewer comparing them is misled. The palette convention (and the
`?relief=` range name) is the smallest shared thing that achieves it. The WebGPU work is a
separate stream; if it comes here, it comes with the upstream's parity-harness discipline
(statistical bounds, device numbers relative-only, no parity claim from a stub).

## 4. Contracts

### 4.1 `pgt-section-pack` v1

A generated JS module (the upstream convention for generated data), guarded like every other
file:

```
SectionPack = {
  format: 'pgt-section-pack', version: 1,
  source: { repo, commit, pack, epochMa, rotModel, built },   // provenance, source of truth
  path:   { kind: 'great-circle', lat0, lon0, az0, closes, arcKm, arcScale },
  planet: { rKm: 6371 },
  n, sKm, lon, lat,          // arc length from the start, degrees
  zM, hFelM, hMafM, hSedM,   // meters, upstream units
  ageMyr, host, owner,       // host = the upstream HOSTS index; owner = upstream plate id
  pot,                       // 6*n, order of Renderer.ORE: oVms oMaf oArc oOro oBas oPla
  sea,                       // { mode, levelM, volumeKm3 } from the upstream water module
  ends, poles,               // local velocity at each end (east/north, m/Myr) and the owning plate's Euler pole
  checksum, license          // checksum over the arrays; license = data/earth/SOURCES.md + License.txt
}
```

Rules: one epoch and one path per pack; generated, never edited; the checksum covers every
array and the source block; `arcScale ≠ 1` is allowed and must be recorded (§4.2); a pack
without a license line is rejected by the loader.

### 4.2 Planet size and the aspect ratio (the hard decision)

The two engines here do not share a planet. The column engine wraps at 2π·6371 km ≈ 40 030 km
with 2 900 km of depth (aspect 13.8, Earth-like). The particle engine wraps at 16 000 km with
the same depth (aspect 5.5) because its convection clock was calibrated there. A real great
circle is 40 030 km, so a pack cannot be 1:1 for both.

Options, with their costs:

| Option | Meaning | Cost |
| --- | --- | --- |
| **A. full circle, compressed** | bake a full great circle and scale the arc to the engine's wrap (`arcScale = wrap / arcKm`), keep the engine's depth and constants | the section is a **schematic** of the real path: lateral distances are 2.5× compressed on a 16 000 km wrap, so absolute lengths and slopes are not Earth's. Honest, cheap, keeps the periodic FFT solve. The pack records the scale and the page prints it |
| **B. window** | bake a 1:1 segment (a plate transect) and run the section with prescribed inflow/outflow ends | needs a non-periodic Stokes solve and end boundary conditions — new physics, P4+ work; until then the model cannot honour the ends |
| **C. re-scale the planet** | make wrap and depth pack-driven and recalibrate Ra, the clock and the fixtures per pack | it re-opens every calibration in the 0.3.0 plan; only justified by a measured need |

**Recommendation: A for 0.9, B as a later, separately planned milestone, C only if a
measurement demands it.** No option may be presented as "the real Earth cross-section" without
the scale factor in the HUD.

### 4.3 URLs

Section packs and runs use the upstream's parameter names, so a URL means the same thing on both
pages: `?start=section&pack=<id>&seed=&dt=&mesh=&preset=`, with `start=earth`/`paleo` reserved
for globe starts. The section pack's id is its file name without the extension and without the
epoch, so `?pack=earth-100Ma-gc0` is unambiguous.

### 4.4 Ledger vocabulary

Upstream distinguishes **stocks** (what is in the world now) from **throughput** (gross
counters); this repository's particle engine prints a ledger against the wall flux and the gap
between them. The contract is the vocabulary, not the numbers: stocks never include throughput,
every transfer is booked on both sides, and a diagnostic that is not conserved is labelled as
such in the readout (the `melt*` star and the HUD's `gap` line are the local form of that rule).

### 4.5 Identity

`(seed, generator version, snapshot checksum)` — upstream's identity triple — becomes the
section's `(seed, version, packChecksum, tileIndex, family, ordinal, drawIndex)`. A catalogue is
reproducible in any order, and a re-import yields the same bodies. The pack checksum is part of
the identity so two packs of the same epoch and path cannot be confused.

### 4.6 Units and clocks

km and Myr for geology, m/Myr for velocities (upstream's convention), meters for elevation on
the pack boundary and kilometres inside the section, dimensionless T/Tm in both. The wall-clock
eruption clock (column engine) and the demo clock (particle engine) stay local; nothing in a
pack or a coupling file carries them, and no geologic constant is written in seconds.

### 4.7 One page, one engine

Both repositories define classic-script globals with the same names (`Params`, `Sim`, `State`,
`Renderer`, `PERF`, and the slice's `P`/`S`/`SIM`) and neither is namespaced. A single page
therefore cannot load the globe's scripts and the slice's column engine together without a
renaming pass. The 0.9 view is **two documents** (an iframe with a `postMessage` handshake, or
two windows), so each engine keeps its own globals; the only shared things are files, URLs and
messages. If a single page is ever wanted, the namespacing pass is a prerequisite milestone, not
a detail.

## 5. Milestones

Each milestone is independently useful and keeps the existing checks green.

### M0 — conventions and provenance (this series' first commit)

`port/PORT.json` and `experiments/port-check.js`; provenance headers on the existing unrecorded
ports (the six potentials, the ore constants, the damage corridor, reference §7.3 routing) with
the upstream commit recorded; `env.js` shared-identical and printed by the harnesses; a
`experiments/run-all.js` short profile; the sync rules copied into AGENTS.md as a short section.

Gate: `port-check` green (zero shared files at this point, all ports headered); a new log's
first line carries the stamp; no engine number changes; every existing check still passes.

### M1 — deposits core

Shared-identical core, priors and economics; the shared draw fixture asserted on both sides;
`snapshotSection` + the section catalogue; JSON round trip.

Gate: §2.5's list, plus body identity holds across two different node runs and across a
save/load once M5 lands.

### M2 — potentials and surface reconciliation

The audit table for every concept both repositories implement (six potentials, arc/oro/basin
production, decay, fertility, host classes, erosion, routing, isostasy): upstream law, local
law, difference, decision. Adopt or declare, one line each.

Gate: the table exists with no blank decision; the mass-accounting fixture closes to 1e-9; the
column engine's numbers move only where a decision says so, with the fixture updated in the same
commit.

### M3 — water level

`water.js` shared-identical, the section's ocean band drawn from the solved level, level and
volume modes, `dry`/`flooded` clamps.

Gate: §2.6's list.

### M4 — the section pack and the slice reconstruction

Globe side: `tools/earth/bake_section.js` emitting `pgt-section-pack`, with a test that the
sampled elevation profile equals the source pack's cells and that the checksum is stable.
Slice side: the generated `js/data/section-<id>.js`, a loader that seeds the column engine
(elevation profile → `zh`, thicknesses → the crust fields, age → initial T, potentials
verbatim), and the page's `?start=section&pack=` path.

Gate: the pack is ≤ 64 KB, carries its license, and reproduces the source pack's profile within
1e-3 relative; the seeded section's seam velocity mismatch is reported and inside the declared
tolerance; the seeded run's HUD prints the arc scale (§4.2); the same pack and seed give the
same state hash on two machines.

### M5 — checkpoint and the coupling envelope

The checkpoint port with a slice-local magic; then `pgt-coupling` v1 — a small JSON the globe
writes every N Myr: time, sea level, per-end velocities, trench positions, ledger stocks — and a
slice mode that reads it. One way only: the section never writes the globe's state.

Gate: save/load round-trips both engines bit-identically; a stale coupling file is refused by
version; in live mode the slice's clock label follows the coupling's time and its end velocities
are set from the file, not from its own spin-up.

### M6 — presentation parity, then GPU

The elevation ramp and ore hues shared; the globe's map, its 3D view and the section agree on
what a colour means. GPU only with the upstream's parity discipline.

## 6. The 0.9 picture this plan prepares

One globe document (geotectonics) and one section document (this repository), side by side, in
sync:

1. the globe draws a path on its map and bakes a `pgt-section-pack` (§4.1) — offline, in the
   browser, from the pack already loaded there;
2. the section page opens with `?start=section&pack=<id>` and reconstructs the profile;
3. the globe posts `pgt-coupling` messages as it runs; the section follows the clock, the sea
   level and its end velocities;
4. the section reports back nothing implicit — a declared, versioned summary at most (crust and
   sediment volume across the path, trench positions), which the globe may display but must not
   fold into its own state without a plan of its own.

Acceptance for 0.9: the same path, epoch and seed give the same pack checksum and the same
section state hash on two machines; a paused globe pauses the section's clock label; with the
coupling file absent, the section still runs standalone and says so.

## 7. Risks and their early warning

| Risk | Warning sign | Counter |
| --- | --- | --- |
| silent drift of a copied law | a constant differs between repositories and no table line explains it | M2's audit table; port headers; port-check |
| vendoring turns into duplication | a shared file is edited locally "just once" | port-check fails; port bumps are the only path |
| the 3D → 2D reduction is mistaken for equivalence | a claim about an ore body's size that only holds in the plane | §2.5's rules; out-of-plane wording in the UI |
| "real Earth" without the scale | a section picture presented as an Earth transect | §4.2: the arc scale is printed on the page |
| unit drift at the boundary | 1000× errors in `z` or velocity | one conversion site per boundary, recorded in §4.6 |
| the second clock leaks into geology | a rate written in seconds in a geologic kernel | §4.6; P3's own contract |
| chasing upstream main | a port that cites a moving target | every port names a commit; bumps are deliberate |
| global-name collision at integration time | a page that loads both engines and misbehaves | §4.7; two documents until a namespacing pass |
| data license | a pack without its `SOURCES.md`/`License.txt` | pack schema requires the license line; loader rejects its absence |

## 8. Cadence

- **Port bump.** One commit that re-records the manifest (upstream commits, hashes), applies the
  deltas, and states in one line what changed. No other commit touches a ported file.
- **Sync audit** at every counterpart release (0.6.2, 0.7.0, …): re-read the divergence table,
  re-run the shared fixtures, and record the result in `archive/`. The audit's output is a short
  document, not a rewrite.
- **Cross-references.** Every plan that touches a shared concept names the counterpart commit it
  was written against, exactly as this plan does.
- **Findings merge.** `findings-pitfalls-skills.md` exists in both repositories and this one's is
  the smaller; insights travel both ways, one bullet at a time.
- **What not to do**: do not port upstream's release-gate claims (60 fps, GPU parity, Earth
  fidelity) into this repository's plans; they are measured on the owner's rig for the globe's
  workloads, and this repository's budgets are its own measured ones.

## 9. Decisions experiments must settle

1. The planet the section models: option A's compression factor per engine, and whether the
   particle engine's clock stays calibrated when a pack's arc scale is not 1 (§4.2).
2. Whether the section catalogue should reuse the globe's cube-sphere tiles (so a body means the
   same thing in both) or its own `(s, y)` tiling (simpler, but the two catalogues diverge).
   Recommendation: its own tiling plus the shared draw fixture; identity is then per-project but
   the *distribution* is shared.
3. Whether instruments on the section read the section slice or the pack's full 3D
   neighbourhood — the honest answer is the second, and it is the reason the pack carries
   `pot` and `host` per cell rather than only the profile.
4. Whether the column engine adopts the upstream's stream-power/hillslope law in M2 or keeps its
   current routing as a declared divergence.
5. The coupling's cadence (every N Myr) and whether a section's own time can run ahead of the
   globe's, or must be slaved to it.
